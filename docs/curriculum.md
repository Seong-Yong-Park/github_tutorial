# 커리큘럼 — 왜 이 순서인가

실행 체크리스트는 `../CHECKLIST.md`에 있습니다. 이 문서는 **각 단계의 의도**만 적습니다.
전체 배경 설명(규모별 운영, repo 경계 7가지 축, 로봇 SW 구조)은 Notion 페이지를 참고하세요.

## 설계 원칙 3가지

1. **읽지 말고 부수기** — 각 Stage에 "💥 일부러 실패해보기" 과제가 있습니다.
   규칙에 막혀본 경험이 규칙을 이해시킵니다. 읽어서 아는 것과는 다릅니다.

2. **더미지만 현실적으로** — `mini-delivery-bot`은 가상이지만 이슈 내용은 실제
   로봇 프로젝트에서 나올 법한 것들입니다. 추상적인 "Task 1, Task 2"로 연습하면
   실제 상황에서 판단이 안 섭니다.

3. **Notion을 처음부터** — 연동을 마지막에 붙이면 그때까지 쌓인 데이터가 규약을
   안 지켜서 결국 다 손봐야 합니다. Stage 0에서 경계를 정하고, Stage 3에서 이슈
   템플릿에 REQ ID 칸을 미리 뚫어둡니다.

## 단계별 의도

| Stage | 새로 생기는 것 | 핵심 깨달음 |
|---|---|---|
| 0 | 도구와 경계 | 어느 쪽이 원본인지 먼저 정한다 |
| 1 | 기록 | 상태는 라벨이 아니라 필드다 |
| 2 | 규칙 | 사람이 지키는 규칙은 안 지켜진다 |
| 3 | 게이트 | 자동화가 규칙을 강제한다 |
| 4 | 계층과 주기 | 나는 2~3배 과대 추정한다 |
| 5 | 조직 | 같은 이슈가 두 보드에 있어도 중복이 아니다 |
| 6 | 연결 | 수동 규약이 안정되기 전에 자동화하면 쓰레기가 2배 |
| 7 | 구조 | repo 경계는 인원수가 아니라 변경 결합도가 정한다 |
| 8 | 확산 | 혼자 쓰면 도입이 아니라 취미다 |

## 진행 규칙

- 시간이 아니라 **완료 조건**으로 넘어갑니다
- 막혔다고 건너뛰지 않되, 한 Stage에 3주 이상 머물지 않습니다
  (그 경우는 과제가 큰 것이므로 범위를 줄이고 나중에 돌아옵니다)
- `_answers/`는 15분 시도한 뒤에만 엽니다
